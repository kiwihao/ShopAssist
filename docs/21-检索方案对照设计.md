# 第 4 块：检索方案对照设计（待确认）

日期：2026-11-02。本文件是方案，混合检索、对照实验和效果结论尚未实现。

## 目标和前置条件

比较当前纯向量检索和一个可解释的混合检索候选，观察固定问题中必要证据的召回变化、错误和耗时；不承诺混合检索一定更好。本项目仅有两款虚拟商品，实验结论只适用于本次数据和配置。

正式对比前先完成并复核固定开发题、独立保留题，以及第 2 块指标脚本和纯向量基线。当前有 20+10 道待用户复核的题集初稿和 4 道标题检查，不能当作正式 Recall 或对照报告。

## 两个方案

- A 基线：沿用现有商品范围过滤后的 BGE-M3 向量检索，返回 Top 3。
- B 候选：同一范围内分别做向量检索和字符匹配，按排名融合后返回 Top 3。

候选方案的第一版拟在 Java 中实现中文字符二元组匹配：对查询和“标题 + 原文”做明确记录的 Unicode 规范化、大小写及空白处理，再以相邻两个非空字符的重合情况排序；数字型号可作为连续字母数字片段补充匹配。短输入、标点、重复片段和无匹配均需有测试并记录实际规则。该方案是小语料下可解释的词法候选，不等同 BM25、中文分词、语义理解或现成生产级全文检索；编码前需以样例确认规则。

本机 PostgreSQL 可用扩展列表包含 `pg_trgm`，但当前没有安装；这里不预设它对中文有效，不以它作为已验证能力。若二元组规则无法满足评测，再另行比较具体中文分词和检索方案。

## 融合与范围

向量和字符候选分别取前 10 条（样本不足取实际数量），对每个片段以 chunk ID 去重；采用倒数排名融合 `1/(60 + 排名)`，两路分数相加，排名从 1 开始。只在一路出现则另一项为 0；总分相同按 chunk ID 稳定排序。60 是本次预设参数，不宣称已调优。

两路必须使用相同的商品 ID、商品状态、生效文档版本与 READY 状态过滤；字符侧应限制在当前可检索的索引空间，避免产生不能与向量基线公平对照的候选。无字符命中时只使用向量排名，不对召回结果凭空补造。任一路失败时不把失败伪装成正常混合结果：评测单独标注错误；产品降级策略需另行确认。

初期允许在**同商品、有效版本且 READY 的小型数据范围**内读取片段做字符评分；需要设置候选/文档规模上限和超限错误，不能声称支持大规模生产。具体上限按现有入库限制和测试确定，超限不得静默截断后冒充完整结果。大规模场景需另设计数据库索引、分页和性能验证。

## 接口与风险

保留现有纯向量接口和响应不变；设计单独的实验调用方式，通过显式参数或独立实验接口选择方案并记录实际模式，默认仍是 vector。实验输出应包含 requestId、各路候选排名、融合排名及分段耗时；候选列表用于本地评测，不放到面向用户的回答里。实际 API 字段、超时、资源上限在实现前明确。

改动只影响实验检索，暂不自动替换页面问答或推荐链路。不得更改商品过滤、扩大文档访问范围，也不能把向量相似度或融合分数当正确概率。

## 评测与验收

1. 两组使用同一批题、语料及版本、模型、topK=3，保留向量基线；在开发集设计、调试，独立保留集留到方案确定后评估一次。
2. 记录每题命中的证据、Hit@3、证据 Recall@3、商品范围违规数、失败、各分母和成功请求的耗时中位数；必要证据按文档及行号映射，人工抽查局部重叠造成的误判。
3. 展示方案改善和退化的题目；模型波动、数据规模和调用成本单独说明。纯检索对比不必调用付费聊天模型。
4. 用测试验证中文/数字匹配、无字符命中、排名融合和同分排序、过滤、各路故障及规模上限；输出真实逐题结果与配置。只有实际运行后才判断是否引入混合检索。

Rerank 另作为可选下一轮：先根据错误案例确认需要，再选本地或云端模型，记录成本和延迟，不与首次混合检索同时改动。用户看到的回答质量与引用支持仍需要人工核对。
