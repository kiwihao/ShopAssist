# 咨询工单：草稿、确认与幂等

日期：2026-11-02。完成本地演示的登记闭环：生成草稿 → 修改核对 → 用户确认 → 创建正式咨询工单。不是订单审核、退款或赔付系统，也未对接真实人工客服。

## 业务与控制边界

Agent 新增 prepare_support_ticket 工具。用户明确要求登记咨询或转人工时，工具保存一份 DRAFT 草稿，保留用户原话，不让模型补写订单、责任或承诺。单纯询问政策仍走知识问答。

正式创建不暴露为模型工具，必须由页面核对按钮调用独立接口。用户在问题里写“已确认”仍只得到草稿。确认令牌只交给页面，在工具结果回传模型前移除，不记录到日志。生成草稿本身会写草稿表，因此不能将三个 Agent 工具统称为只读。

本轮没有登录身份和用户隔离，令牌只绑定确认内容，不是用户认证；接口仅限本地演示，不应当作为生产权限控制证明。

## 数据与状态

- ticket_drafts：商品 ID、咨询原文、版本、确认令牌哈希、有效期和 DRAFT/CREATED/CANCELLED 状态。
- consultation_tickets：正式编号、草稿 ID、商品和文本快照、确认版本、令牌哈希、幂等键和 OPEN 状态。
- 草稿有效期30分钟。修改时版本加一、替换令牌并重新计时；旧版本和旧令牌不能提交。
- CREATED 和 CANCELLED 草稿不能编辑或重新创建。正式工单本轮没有处理、关闭或退款状态流转。

## 为什么重复请求不会多建工单

创建在 Java 事务中执行：锁定草稿行 → 校验版本和令牌 → 核对幂等键 → 查询既有工单 → 检查状态/有效期 → 插入快照 → 标记草稿 CREATED。

数据库同时设置 draft_id UNIQUE 和 idempotency_key UNIQUE。行锁使同一草稿的确认串行处理；唯一约束保护同键跨草稿并发。相同确认重试返回原工单、replayed=true；同键指向另一草稿返回409。相同草稿换键也不会再建第二张。

幂等范围是同一草稿，不是“相同自然语言永远只有一张工单”。用户主动重新生成的另一份草稿可以创建另一张工单。已经创建的正确重试在草稿有效期过后仍返回原结果。

## 接口

| 接口 | 行为 |
| --- | --- |
| POST /api/ticket-drafts | productId、summary，保存草稿并返回版本和确认令牌 |
| PUT /api/ticket-drafts/{id} | version、confirmationToken、summary，修改并返回新版本/令牌 |
| POST /api/ticket-drafts/{id}/cancel | version、confirmationToken，取消草稿 |
| POST /api/ticket-drafts/{id}/confirm | Idempotency-Key 请求头；正文含 version、confirmationToken、confirmed=true |

创建及重放均返回200，响应含 ticket_id、ticket_number、summary、status、replayed。取消/修改不代表正式创建。错误覆盖确认缺失400、令牌错误403、草稿不存在404、版本/幂等键/状态冲突409、过期410。

## 页面

开启“客服自动选工具”，例如输入“演示咨询：背包拉链无法拉合，请登记咨询工单”。草稿支持编辑，保存修改后必须重新核对；勾选当前内容后才启用“确认创建工单”。正式结果显示编号与登记内容，取消则明确没有创建。

客户端幂等键稳定绑定草稿 ID 与版本。确认结果不明时，临时禁止修改/取消，保留原键重试；页面中的草稿更新、取消及创建结果按商品随问答记录保留。刷新页面仍会丢失内存记录，本轮没有持久会话或工单查询入口。修改草稿响应丢失后的恢复、跨设备恢复、权限和处理后台留待后续。

## 实际验证

1. 默认 Java 测试45条通过，12条集成用例按开关跳过，无失败。
2. 专用 PostgreSQL 数据库 ecommerce_rag_ticket_test 单独运行7条测试，全部通过：草稿不创建正式工单、显式确认、编辑后旧版本/令牌失效、同键/换键重试、跨草稿键冲突、六个并发请求只产生一行、取消/过期/错误令牌阻断、成功响应丢失后的过期重放。
3. Agent 模拟测试确认：包含“我已确认”的用户文本仍只调用 prepare，且回传模型的结果中没有确认令牌。
4. 真实 Agent 生成草稿后直接查询正式工单表，该草稿记录数为0。
5. 真实浏览器走通编辑到版本2、重新核对、确认创建。额外在测试浏览器中故意丢弃服务端成功响应，重试使用同一键，返回同一工单 ID；查询该草稿的正式记录数为1。
6. 更新后的页面验证：切换商品再返回，版本2与修改文本保留；创建结果保留；另一份草稿取消后明确显示未创建。
7. 6项接口脚本用例在 PowerShell 7 和 Windows PowerShell 5.1 下通过。前端类型检查与构建通过。

浏览器故障注入只作用于测试页面的 fetch，测试后已恢复；没有修改生产代码制造假成功。截图在 .runtime/ticket-draft.png、ticket-lost-response.png、ticket-created-final.png；均为虚拟演示数据。

## 复验

后端启动后，在仓库根目录执行：

```powershell
.\scripts\check-tickets.ps1
```

脚本会真实创建一张本地演示工单、取消另一份草稿，不能把它当作只读检查。报告 .runtime/ticket-results.json 不保存确认令牌，不纳入 Git。

数据库测试先创建上述专用测试库，然后在 server/ 执行：

```powershell
$env:DEMO_INTEGRATION_TESTS='true'
.\mvnw.cmd '-Dtest=TicketIntegrationTest' test
Remove-Item Env:DEMO_INTEGRATION_TESTS
```

CI 已增加独立临时 PostgreSQL 服务执行这7条测试，不使用聊天模型密钥。并发验证只证明此测试负载下正确，不是压测指标。
