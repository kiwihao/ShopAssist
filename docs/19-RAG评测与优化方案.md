# ShopAssist RAG 评测与优化方案（待确认）

日期：2026-11-02。本文是下一阶段方案，不代表计划功能已实现或指标已达标。

## 1. 定位和目标

对当前虚拟电商商品问答建立可重复的评测：先判断检索能否找到必要资料，再人工核对回答及其引用，最后依据失败案例决定是否优化。目标是积累可复现的工程与面试证据，而非在两款演示商品上宣称生产效果。

## 2. 当前状态与边界

- 已实现：Markdown 分块、BGE-M3 向量化、按商品和有效版本过滤的 pgvector 精确余弦检索，以及带引用回答。
- 已验证：4 道固定题的目标标题检查；少量真实问答及手洗题人工核对。当前标题命中检查不是正式 Recall；只用标题不能证明具体证据充分。
- 尚未实现：本方案的数据集、指标脚本、人工标注汇总、混合检索、Rerank、基于固定集的方案对比。当前没有证明任何方案是最优方案。
- 数据均为虚拟商品资料；不涉及用户隔离、真实客服运营数据或真实商家的承诺。生成内容的语义判断先由人完成，不把关键词规则或模型评分当作正确性的证明。

## 3. 数据集与标注

1. 第一阶段拟准备 20 条左右开发题，覆盖：两商品尺寸、清洗差异、隔层、缺失承重、电脑适配追问，以及同一事实的不同问法。可答、资料不足和需追问分开标记。
2. 每题记录题目 ID、商品 ID、问题、期望类型、期望事实、来源文档及版本、对应标题和行号范围；可有多个必要证据。明确不知道答案时也标注资料中说明信息缺失的证据，不能把它当成无证据题。
3. 必要证据先以文档版本及行号范围标识，避免仅依赖每次入库可能变化的 chunk ID。评测时按同文档、同版本且与标注行范围有重叠的片段映射；若跨分块且仅有部分内容，仍需人工复核，不能把行号重叠当成充分证据的保证。文件内容变更要重标，固定语料版本。
4. 另预留约 10 条独立题作为保留集，不参与提示词或参数调试；题目数量是实施目标，完成和人工检查前不算已建成。数据集需与知识库文件分开，标准答案不能入库。
5. 每题记录人工核对者、版本和有歧义的判定；不确定题先修订标注或单独列出，不强行计入通过。

## 4. 具体指标与统计口径

| 指标 | 计算口径 | 用途与限制 |
| --- | --- | --- |
| Hit@3 | 有标注证据且调用成功的题中，前 3 条至少命中一个必要证据的题数 / 该类成功调用题数 | 看是否至少找到一条；多证据问题可能只找到一部分。 |
| 证据 Recall@3 | 每题命中的必要证据数 / 该题必要证据总数，再对有标注证据且调用成功的题取宏平均 | 多证据题不会因只命中一条就得满分；当前先用行号重叠近似映射，需人工抽检。 |
| 商品范围违规数 | 成功检索结果中返回非指定商品片段的请求数 | 安全边界检查，单独报告，不和语义质量混成一个分数。 |
| 人工回答通过率 | 人工判为通过的成功问答数 / 已人工判定的成功问答数 | 核对事实、遗漏、无依据推断、追问或拒答是否合适；有歧义单列，不排除错误后冒充整体成功率。 |
| 引用支持情况 | 人工逐题检查关键事实是否被所引原文支持；报告通过 / 已判定和未判定题数 | 引用存在不等于引用支持结论；目前不逐句自动打分。 |
| 错误与耗时 | 请求总数、成功数、HTTP/超时错误数；成功请求分别汇总检索 `embeddingMs`、`searchMs`、`elapsedMs`，提供中位数及样本数 | 先不对少量样本的 P95 做稳定性结论；完整问答端到端耗时需要客户端另行测量。 |

没有标注证据、未人工判定和调用失败的题不进入相应质量分母；总题数、各分母、错误和未判定数都必须同时展示。人工核对资料不足类题是否给出保守回答。当前模型接口没有稳定可用的完整 token 用量或价格证据时，记录调用次数和模型名，不估算费用。

## 5. 对照实验设计

基线为现有纯向量检索，固定商品资料版本、分块、模型 `bge-m3:567m`、topK=3、题目、代码版本、运行配置。记录检索模型与实际服务响应、语料版本、日期、每题请求及片段；问答另记录聊天模型、提示词版本、回答和引用。

先建立基线并分析失败，再选择一个变量进行对照：优先考虑关键词检索与向量检索融合；先确定中文关键词分词、融合排序、过滤范围与实现成本，再编码。Rerank 等后续选项等混合检索实验后判断是否值得实现。不同分块方式改变片段边界，需要重新映射并复核证据标注；不同 embedding 需要重新索引，不能混用向量空间。

同一批问题分别运行两个方案，记录逐题变化、成功和错误数以及耗时；生成模型可能有随机波动，必要时重复调用并保留每次结果，不能把一次不同回答当成稳定提升。只基于评测结果讨论本演示条件下的取舍。

## 6. 阶段开发与验收

1. **确定方案与数据**：确认分类及标注规则，人工整理开发题、保留题与证据。验收：每题可在原文定位证据或明确说明不可回答的原因，无题目混入知识库。
2. **检索基线脚本**：扩展 Python 读取标注、逐题调用，输出上表检索指标与错误清单，保存带版本的逐题结果。验收：人工抽查多证据题和商品过滤，指标计算能用小例子复核；接口错误单独报告。
3. **回答人工评测**：记录问题、回答、引用、逐题判断和失败原因；支持标注待复核。验收：可按回答错误、证据不足、引用不支持、请求错误等分类查看；不依赖自动关键词宣称事实正确。
4. **一次检索对照**：选定并实现一个明确的候选方案，在同一固定集运行对比。验收：同一配置下的结果与逐题变化可复现，解释至少一条失败案例及取舍。
5. **总结与面试准备**：写实现步骤、观察结果、成本和限制。验收：每条简历表述都能对应实际代码及记录，无未经验证的性能数字。

每阶段遵循讲解、操作、验证、复盘；模型请求产生真实费用。上一阶段结果可用后再进入下一阶段，方案可根据实际失败案例调整。

## 7. 后续项目范围

当前 Agent 是 Java 原生工具循环，已支持知识检索、推荐条件准备和工单草稿；本阶段不引入新框架。Python/LangGraph 后续单独做一条可解释的小链路，服务于学习目标，不重写整个项目。MCP、Skills、长期记忆和真实用户隔离不属于本阶段验收。
